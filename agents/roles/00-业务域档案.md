## 一、这家公司在卖什么，这条线为什么存在

### 1.1 生意的形状

深信服是 **ToB 的网络安全与云计算厂商**。它卖的东西有三个特点，直接决定了系统的复杂度：

| 特点 | 对系统的影响 |
| --- | --- |
| **软硬一体交付** | 一个产品在报价单上是一个「销售型号」，在仓库里是一堆「物料」，在工厂里是一张 BOM。三者不是一对一 |
| **配置可变化** | 同一型号可以配不同内存/硬盘/网卡。涨价、缺料、换料都会导致「型号没变但配置变了」 |
| **渠道 + 直销并存** | 订单从销售、渠道、合作伙伴多个口子进来，报价单可能被复制、转存、改价 |

**所以内部系统的核心任务不是「好看」，是「不让钱和货算错」。**

### 1.2 使用者的位置

使用者是**这条线上的产品经理**（一个人一条线，没有团队）。他：

- 上游对接：业务方（销售/商务/财务 BP/采购/交付）、主管
- 下游对接：开发、测试、主数据管理员、系统运维
- 手里同时压着 3～8 个需求，每个在不同阶段
- 材料来源：企微会议纪要、邮件、业务方给的 Word/Excel、旧 PRD、Demo、UAT 反馈

**他的痛点不是「写不出东西」，是「记不住、对不上、反复推」。**

### 1.3 这个岗位的价值怎么衡量

不要用 DAU、转化率、留存那套 C 端语言。这里的价值是：

| 说得出口的价值 | 说不出口但更真实的价值 |
| --- | --- |
| 单据不再重复计算，财务不用手工对账 | 月底结账少加两天班 |
| 两个系统口径打通，业务只查一个地方 | 业务不再打电话问「这个数为什么对不上」 |
| 配置切换不出错，不会发错货 | 不会有一单发错造成退货和赔偿 |
| 权限收紧但流程还能走 | 合作供应商不会因为看不到信息而卡住发货 |
| 需求池里的活能被看见、能排期 | 自己不用每周手工汇总进度 |

**写立项报告、写 PRD 开篇、跟主管汇报时，用左列的语言；跟开发对齐时，用接口和规则的语言。**

## 二、系统全景：这些系统各自管什么

### 2.1 五层结构

```
┌─ 协同层 ── OA / 企微 / 研效通 / 邮件 ──────────── 人和流程在这层
├─ 财经层 ── 预算 / 管报 / 成本存货 / 应收应付 / 资金 ── 钱在这层
├─ 交易层 ── CPQ·SCP / D365 / OMS ──────────────── 单在这层
├─ 供应层 ── 盘古供 / 供应能力中心 / ATP / ERP / SRM·SCC ── 货在这层
└─ 主数据 ── MDM / PLM / BOM ─────────────────── 定义在这层
```

**一条铁律：上层只能消费下层，不能反向定义。** 报价单不能自己算库存，ATP 不能自己判断配置切换日期，报表不能自己重算口径。

### 2.2 逐系统速查

| 系统 | 全称/定位 | 它权威的东西 | 常见坑 |
| --- | --- | --- | --- |
| **CPQ / SCP** | 配置报价 / 销售协同平台 | 报价单、选配结果、折扣 | 报价单可被复制转存，创建日期失真 |
| **D365** | CRM | 客户、商机、销售归属 | 与 OMS 的客户/商机口径容易错位 |
| **OMS** | 订单管理系统 | 销售订单、订单行、订单状态 | 订单行的配置是下单瞬间的快照 |
| **盘古供** | 供应链系统 | 供应能力、ATP 输入、型号物料映射、要货建议、履行计划、策略性备货 | 型号映射一对多，汇总极易重复 |
| **供应能力中心** | 供应能力计算引擎 | 可承诺量 | 15 分钟级刷新，别要求实时 |
| **ATP** | 可承诺量承诺 | 按物料过滤后的可承诺库存 | **只消费 OMS 下传的结果，不自行判断切换日期** |
| **ERP / Oracle EBS** | 企业资源计划 | 库存、子库、选配登记、发货/搬运单、采购订单、BOM、标准成本 | 子库与组织维度多，取数必须指定 |
| **SRM / SCC** | 供应商协同 | 供应商、配额、送货单、交期回复、长周期备料 | 供应商侧数据质量参差 |
| **PLM** | 产品生命周期 | BOM、物料、生命周期状态 | 是源头，但不等于当前可用 |
| **MDM** | 主数据管理 | 销售型号、物料属性、销售物料成本、管报科目 | 分发有延迟，缺失时要兜底 |
| **BI / FineBI** | 报表 | 加工后的指标 | 4 小时级刷新，与业务系统天然不同步 |
| **财经截止性数据** | 库存看板的财经口径 | 销售未出库 | 与「未备」不是一回事 |
| **OA / 企微** | 审批与协同 | 审批流、会议纪要、文档 | 纪要是自然语言，要转成规则 |
| **研效通** | 研发效能平台 | 需求池（REQ）、任务（TASK）、缺陷（TD）、迭代 | 开放 API **不能设上级需求、不能传附件** |

### 2.3 三条端到端主线

**OTC（Order to Cash，订单到回款）**
`CPQ/SCP 报价 → D365 商机 → OMS 订单 → （ATP 承诺）→ ERP 挑库发货 → 应收 → 回款核销`

**计划到库存**
`销售预测 → 要货建议 → 履行计划 → 采购（SRM）→ 收货 → 库存与供应能力`

**PTP（Procure to Pay，采购到付款）**
`采购申请 → 采购订单 → 到货 → 对账 → 应付 → 付款`

> 写任何一个需求前，先回答：「它插在这三条线的哪一段？」
> 答不出来，说明还没摸清楚，别动笔。

## 三、一条订单的生命周期（最该背下来的对象链）

| 环节 | 产生什么 | 关键字段 | 谁负责 | 常见问题 |
| --- | --- | --- | --- | --- |
| 商机 | 商机号、客户、金额 | 客户主体、预计成交 | 销售 | 客户主体与合同主体不一致 |
| 报价 | 报价单号、配置、价格 | **报价单创建日期**、有效期、配置明细 | 销售/售前 | 复制转存后日期失真 |
| 选配 | 配置清单、物料展开 | 销售型号、组件、物料编码 | 售前/产品 | 配置合法但物料缺货 |
| 下单 | 销售订单、订单行 | 订单号、行号、数量、交期 | 商务/销售 | 一单多行、一行多配置 |
| 承诺 | ATP 承诺日期/数量 | 物料、可用量、承诺口径 | 供应链 | 承诺了但没锁库存 |
| 挑库/备货 | 挑库单、锁定库存 | 子库、批次、序列号 | 仓储 | 挑了但没发，库存被占住 |
| 发货 | 搬运单/发货单 | 出库单号、实发数量 | 仓储/物流 | 部分发货、拆单 |
| 出库 | 库存减少、成本结转 | 出库日期（财经截止性） | 财务 | 单据日期 vs 实际出库日期 |
| 应收 | 应收单、发票 | 金额、税率、账期 | 财务 | 与订单金额差异（折扣/返利） |
| 回款 | 收款单 | 到账金额、到账日期 | 财务 | 一笔记多单、多笔记一单 |
| 核销 | 核销关系 | 收款↔应收 | 财务 | 核销规则不透明，业务看不懂 |

**这张表是 Shouter 回答「这个数从哪来」的底牌，也是 Writer 写「数据来源」列的字典。**

## 四、配置与型号：这个行业最难的坑

### 4.1 五个「型号」不是一回事

```
销售型号（客户看到的 SKU，报价单上写的）
   └─ 1:N ─ 供应链型号（备货、ATP 用的）
        └─ 1:N ─ 硬件型号（生产/结构用的）
             └─ 1:N ─ 物料编码 / 家族料号 family_code（库存、采购用的）
```

**这对需求的影响：**

- 任何「按型号统计」的需求，先问：**按哪一层型号？会不会把同一个实物算了两遍？**
- 销售型号的库存 ≠ 实物库存。销售型号维度做汇总，天然会重复。
- 报表明细下钻，必须能落到物料编码，否则财务对不上。

### 4.2 配置会变，流程要跟得上

| 概念 | 人话 |
| --- | --- |
| **BOM** | 物料清单：一个产品由哪些料组成 |
| **选配** | 客户选的具体组合（内存/硬盘/网卡） |
| **选配登记** | 在 ERP 里把「这单要什么配置」记下来，供生产和发货用 |
| **配置变更** | 同一型号换了组件（涨价、缺料、停产替代） |
| **ECN** | 工程变更通知：正式宣布「从某天起按新配置」 |
| **切换点** | 新旧配置的分界线。**用哪个字段当分界线，是整个需求成败的关键** |

**示例**：组件价格变化，需要在型号不变时更换配置。需求要判断订单适用新配置还是旧配置。
假设使用**报价单创建日期**作为基准，还需考虑复制或转存报价单后日期是否仍能反映选型时间。
这条没钉死，整个判断基准就是空的。**这就是为什么「时间边界」在本领域永远是第一优先级。**

## 五、库存与供应能力的六个「数」

这六个数字长得很像，含义完全不同，**混用一次就会被业务当场抓住**。

| 数 | 定义 | 谁算的 | 刷新 | 能用来 | 不能用来看 |
| --- | --- | --- | --- | --- | --- |
| **未备** | 销售订单还没备货的数量 | 盘古供/供应能力 | 15 分钟级 | 判断「还能不能接单」 | 账面库存 |
| **已备** | 已备货未发货 | 供应链 | 准实时 | 看在手待发 | 可用库存（已被占） |
| **未发** | 销售未出库（财经截止性口径） | 财经 | 按日/按结账 | 库存看板、财经口径 | 供应能力 |
| **已发** | 已出库 | ERP | 实时 | 出库统计 | 收入（还有确认问题） |
| **锁库** | 被挑库/预留占住 | ERP/仓储 | 实时 | 解释「为什么有库存却发不出」 | 总量 |
| **采购在途** | 已下单未到货 | SRM/ERP | 按单 | 判断未来可供 | 当前可用 |

**示例**：同一型号的供应能力显示「累计未备订单 10」，库存报表显示「销售未出库 20」。
不是谁算错了，是口径不同。**写需求时把这种差异解释清楚，比让两个数强行相等有价值得多。**

### 5.1 刷新频率的现实

- 供应能力：**15 分钟**级
- BI / FineBI：**4 小时**级
- ERP 库存：准实时
- MDM 主数据分发：有延迟（小时级，具体 `[待确认]`）

**所以「与 XX 系统实时一致」这种需求，技术上就是不可实现的。**
正确的写法是三段：以谁为准 / 允许多大延迟 / 不一致时界面怎么表现（提示？置灰？显示口径说明？）。

## 六、财经侧：钱是怎么记的

### 6.1 预算（使用者做过的完整重构）

一个预算系统的最小闭环：

```
年初预算（按部门 × 科目 × 年度）
  → 追加预算（年中加钱）
  → 调整（预算在科目/部门之间挪）
  → 消耗（实际发生，来自采购/费用/请款）
  → 剩余 = 年初 + 追加 + 调整 - 消耗
```

**这个领域最容易犯的错是重复计算。** 真实系统里，同一个预算被三条路径消耗过：
采购申请、请款单、核销明细。写规则时必须说清：
「消耗取哪几张表、按什么键关联、同一个业务对象只能计一次，重复时以哪条为准。」

### 6.2 管报与科目

- **管报**（管理报表）：给内部经营分析用的口径，和法定报表不完全一样
- **管报科目**：一套独立的科目体系，与财务科目有映射关系
- **财务映射**：管报科目 ↔ 财务科目 ↔ 成本中心的对应表
- **款项类型**：收付款的业务分类（货款、服务费、保证金…），影响核销和报表

**跨系统映射类需求（如"财务映射"），第一个要问的永远是：映射关系谁维护？映射不上时怎么办？**

### 6.3 结账节奏（写「时效」需求时的唯一依据）

- 总账结账后 **+3 工作日**出费用与资产数据；收入成本 **+1**；BP 经营分析结论 **+2**；现金流 **+1.5** 汇总再 **+1.5** 提交
- 季度：结账 → **+4** 上数 → **+1** 提交 → **+2** Forecast → **+1** 整体报告 → **+2** 集团分析

**任何「T+1 就能看到」的需求，都要拿这张表核对一遍。** 对方说「结账后马上要」，你得回答「结账后第几天，因为费用和资产要 +3」。

## 七、主数据：一切的源头

- **MDM 分发**：销售型号、物料属性、销售物料成本、管报科目
- **PLM 是 BOM / 物料 / 生命周期的源头**
- 主数据的三个现实：
  1. **有延迟**：分发不是实时的
  2. **会缺失**：新物料还没分发下来，系统要能兜底
  3. **名称不可判重**：`名称只用于展示，判重以主数据标识（编码/ID）为依据`

**兜底写法（照抄就行）**：
「主数据未分发到位时，页面显示 `—` 并提示『主数据待同步』，不阻断其他字段的展示与操作；
用户刷新后重试。不得用名称、简称或历史缓存值代替主数据标识。」

## 十、常见需求类型，和它们的「标答结构」

> 使用者 80% 的需求落在这七类里。每一类都有固定的必问问题和最容易漏的地方。

### 10.1 加字段 / 小改（小需求主力）

- **必问**：字段从哪来（源表+字段名）？谁维护？为空时显示什么？谁能看？改动影响哪些下游？
- **最容易漏**：空值处理、历史数据回刷、下游报表是否要同步加列
- **验收**：这条字段在 A 场景显示什么、B 场景显示什么，一条一句

### 10.2 加一个报表 / 看板

- **必问**：指标定义（分子分母）？时间边界？分组维度？刷新频率？数据权限按什么维度切？
- **最容易漏**：型号维度重复汇总、跨年数据、口径与既有报表打架
- **验收**：给一组可复算的样例数据（含边界与空值）

### 10.3 系统间对接

- **必问**：谁是主？谁触发？失败重试几次？幂等键是什么？对账怎么做？字段映射表在哪？
- **最容易漏**：乱序到达、部分成功、重复推送、时钟不一致
- **验收**：正常一条、重复一条、失败一条、乱序一组，各自结果

### 10.4 权限与脱敏

- **必问**：按什么维度授权（组织/角色/客户/供应商）？服务端还是前端？脱敏后哪些操作**必须仍然可用**？
- **最容易漏**：导出、打印、接口直连、二次查询绕过
- **验收**：无权限账号调用接口返回什么（必须是已脱敏/已拒绝，不能返回后前端隐藏）

### 10.5 配置切换 / 版本切换

- **必问**：切换基准字段是哪个？切换时刻边界（含当天）？切换前已下单未发货怎么办？切换后老配置还能不能查？
- **最容易漏**：报价单转存导致基准失真、跨系统时钟不一致、售后查历史配置
- **验收**：切换前一天/当天/后一天各一张单，结果分别是什么

### 10.6 流程线上化（审批、待办）

- **必问**：节点与角色？会签还是或签？驳回回到哪？超时怎么办？代理/离职怎么处理？
- **最容易漏**：状态机不闭合（卡在中间态无法前进）、并发审批、撤回
- **验收**：正常走完、驳回重提、超时提醒、节点无人时兜底

### 10.7 数据回刷 / 历史修复

- **必问**：影响多少条？回刷期间业务能不能用？回刷失败怎么回滚？回刷后对账谁做？
- **最容易漏**：回刷把手工修正过的数据覆盖掉、回刷期间产生的新数据漏掉
- **验收**：回刷前后对账表（条数、金额、关键分组），逐项一致

## 十一、什么叫「这个需求做对了」

四条判据，每次交付前自己过一遍：

1. **可复算**：业务拿着你写的规则，能自己算出一个数和系统一致。
2. **可核对**：每条验收标准是一句能被业务点着屏幕说「对/不对」的话，不是「功能正常」。
3. **可兜底**：空数据、无权限、接口超时、主数据缺失，四种情况都有明确表现。
4. **可追溯**：每个结论能说出「谁在什么时候说的」或「哪份文档第几节」。

**反例（见到就是没做对）：**

- 「与 BI 保持一致」——没写清以谁为准、允许多大延迟
- 「权限：隐藏」——没说服务端做，没说脱敏后还能干什么
- 「验收：功能正常」——业务没法核对
- 「数据来源：系统」——等于没说
- 「默认值 0」——使用者明令禁止

## 十二、禁区（碰了就是事故）

1. **不复述凭据**：账号、密码、令牌、Basic Auth、手机号、身份证、完整地址，任何输出都不能出现。
   已知风险点：《SXFEBSIF-001-获取搬运单接口》里有明文 Basic Auth，读到跳过。
2. **不声称已验证**：没有代码仓库、测试库、生产权限。说「我查过了」必须说清查的是文档还是系统。
3. **不替业务拍板**：规则冲突、口径取舍、优先级，一律列成问题给他决定。
4. **不虚构**：人、工时、排期、指标基线，没来源就不写。
5. **不动生产数据**：不代签审批，不改库，不手工补单。
